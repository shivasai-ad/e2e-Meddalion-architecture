01 What is medallion architecture

In plain English, before any Databricks-specific detail.

A "medallion" pipeline is just a rule about where in a chain of tables each kind of work is allowed to happen. Data comes in messy and raw; it leaves clean and business-ready. In between, it passes through three checkpoints, each with exactly one job:

Bronze

Keep everything, forever, exactly as it changed

Bronze's only responsibility is history. Every version of every row that ever existed stays here — closed, never deleted, never overwritten. If this layer is lost, the past is unrecoverable.

Silver

Clean it up, current state only

Silver answers "what does this record look like right now?" — trimmed, type-cast, flagged where something's missing. No history, no business rules. Just a tidy current snapshot.

Gold

Answer the business question

Gold is the only layer allowed to contain business logic: counts, KPIs, cross-entity joins. It's rebuilt from Silver/Bronze every run, so a KPI definition can change without ever touching ingestion.

The reason this discipline matters: without it, teams tend to bury a "current state" filter three notebooks deep, or let a dashboard's business rule silently start living inside the ingestion job. Six months later, nobody can say which layer owns which decision. Medallion architecture is the fix — a place for every kind of logic, and only one place.

02 This harness, at a glance

What DAA-856 asked for, and the one deliberate choice that shapes everything below.

DAA-856 asks for end-to-end tests proving a medallion pipeline works: CDC capture, CDF propagation, data quality, audit logging. The pattern itself is documented in this repo at docs/databricks_objects/15_medallion_pattern_rds_to_databricks/medallion-cdc-fed-pattern.md, and it's already implemented for real in the Payments team's pipeline.

This harness tests the pattern, not Payments' pipeline. It builds its own tiny, synthetic orders entity and its own Bronze/Silver/Gold tables, entirely decoupled from any real team's data. The "source" is a plain Delta table with Change Data Feed switched on — Delta doesn't care who writes to it, so mutating it directly with SQL produces real CDF events, the same shape a real CDC connector would produce, without needing one.

Why rls_testing as the catalog? Every domain catalog in this workspace (Payments, FOF, etc.) is Terraform-managed and only grants write access to that domain's own engineers. rls_testing is the one catalog that grants this harness's owner full privileges directly, with no new grant needed, and no relationship to any domain's real data. Swap the catalog bundle variable to point somewhere else later.
External tables — and a lesson in not trusting one check. The doc's own examples use external Delta tables at an explicit s3://ad-dna-{region}-{env}-datalake-{layer}-{account_id}/ location. All 6 tables here now do too. Getting there took two contradictory findings: reading grants directly (databricks grants get external_location ...) showed only the data-engineers group holds CREATE_EXTERNAL_TABLE/WRITE_FILES on these buckets — this harness's owner isn't a member, so the first conclusion was "managed tables only." An actual CREATE TABLE ... LOCATION ... attempt then succeeded completely. The reconciliation: this workspace's metastore is owned by an account-level metastore-admins group, which has implicit access to every securable in the metastore regardless of that object's own explicit grant list — invisible to a grants check on the object itself. Lesson: test the actual operation, don't just read the grant list.

04 How it runs — the execution flow

What runs after what, and which file is responsible for each step.

What each file actually is

FileWhat it does
common/config.pyThe one place the orders entity's shape lives: schema names, key column, which column to exclude from the hash, the sequence column.
common/ddl.pyBuilds CREATE TABLE SQL for staging + Bronze, including the LOCATION clause when external tables are on.
common/scd2.pyBronze's core mechanics: row_hash(), read_changes() (CDF or full snapshot), latest_per_key(), classify().
common/job_flags.pyThe doc's own prescribed watermark store — generic get/set on a (job_name, key, value) table.
common/control.pyThin adapter: get_watermark/set_watermark on top of job_flags.
common/audit_log.pyAuditLogger — logs every write's success/failure/duration, and decomposes a MERGE's metrics into 3 rows.
common/pipeline.pyThe actual pipeline. ensure_environment(), reset_environment(), run_bronze(), run_silver(), run_gold() — every notebook and every test calls into this file, nowhere else.
Why two jobs, not one? Not a doc requirement — the doc says nothing about job/test orchestration. It's the fix for a real collision: pytest needs a guaranteed-clean state before every test, but that's exactly wrong for a pipeline run, which should never destroy data you just inserted by hand. e2e_medallion_pipeline (safe, never destroys your data) and e2e_medallion_tests (resets to a known baseline every time, on purpose) are separate precisely so neither behavior leaks into the other. Never run both at once — they hit the same fixed external table locations and will collide.

05 How to run it

The commands actually used to build this guide, plus the UI equivalent.

Two separate jobs, deliberately not chained together — running the pipeline should never accidentally trigger a reset-everything test run as a side effect.

From the terminal

# one-time: validate, then deploy
cd examples/e2e_medallion_pattern_test_copy
databricks bundle validate --profile adi
databricks bundle deploy -t dev --profile adi

# run the pipeline on whatever is in staging right now (reset defaults to false)
databricks bundle run e2e_medallion_pipeline -t dev --profile adi

# ...or force a clean slate first
databricks bundle run e2e_medallion_pipeline --params reset=true -t dev --profile adi

# run the automated test suite (this one resets data as part of testing)
databricks bundle run e2e_medallion_tests -t dev --profile adi

From the Databricks UI

  1. Left sidebar → Workflows → Jobs tab
  2. Find "E2E Medallion Pipeline" (setup → bronze → silver → gold) or "E2E Medallion Tests" (just the pytest suite)
  3. Click Run now (top right)
  4. Click into the run — watch the live DAG. Click any box for that task's live notebook output.

Or open any notebook directly under the workspace path above, attach it to serverless compute, and Run All — the best way to poke at one layer in isolation after editing the staging table by hand.

06 The 8 architecture rules

What "follows the pattern" cashes out to, concretely — and where each rule is enforced and proven.

01

History lives only in Bronze

Silver and Gold never re-derive it, and neither copies it downstream. A point-in-time projection could be built from Bronze's own columns later with zero backfill — deferred for now since nothing consumes one (doc: "build it only if you have a consumer").

common/pipeline.py::run_bronzetest_tc002_004
02

Change detection is a hash, not a full compare

MD5 over sorted business columns, NULL-safe. Reordering the column list is a breaking change by design.

common/scd2.py::row_hash
03

CDF drives incremental reads, never a full rescan

Bronze reads exactly table_changes(from_version+1, to_version) — the slice since the last watermark.

common/scd2.py::read_changes
04

The watermark advances only after a successful write

If Bronze's MERGE ever failed mid-way, the watermark stays put and the next run safely replays the same range.

common/control.py::set_watermarktest_tc005
05

Replaying a run is a no-op

Unchanged rows are classified UNCHANGED and dropped before either write happens.

common/scd2.py::classifytest_tc005_tc403
06

Silver is current-state + cleansing only, never business logic

WHERE _bronze_is_current = TRUE, then trims, casts, and data-quality flags. Nothing else.

common/pipeline.py::run_silvertest_tc102
07

Gold is business logic, rebuilt every run

A full CREATE OR REPLACE each time — always safely rebuildable, so a KPI definition can change with zero backfill.

common/pipeline.py::run_goldtest_tc203
08

Deletes are soft, never physical

A delete closes the current Bronze version — is_current=false — and inserts nothing. The row is never removed.

common/pipeline.py::run_bronzetest_tc002_004

An exhaustive, section-by-section comparison against medallion-cdc-fed-pattern.md: for every rule, mechanic, and column the doc specifies, is it here? Full detail in README.md — this is the presentation-sized version.

✓

Architecture, layer roles, naming convention

4-stage flow, "history lives in exactly one place," every audit column _-prefixed — all present, exactly as documented.

✓

Every column name, all 6 tables

Bronze's 5, Silver's 6, Gold's 1, job_flags' 9, audit_log's 18, plus Staging's _rescued_data — verified live via DESCRIBE TABLE, verbatim matches.

✓

External tables, at the doc's exact S3 convention

formatted_stg/formatted/published/audit prefixes, all 6 tables — see §2 for how this was actually confirmed.

✓

Control table (job_flags) and audit log (audit_log)

Exact DDL, exact API, log_merge() behavior all verified live against real MERGE operations.

4

Deliberate, documented deviations

Hash excludes updated_at; Bronze writes in two steps (MERGE + append) instead of one atomic UNION ALL MERGE; Silver does SELECT *-then-drop instead of an explicit column list; Silver fully rebuilds every run instead of an incremental MERGE. All four are the same choices the real Payments pipeline makes, inherited on purpose, each with a documented reason — not oversights.

✓

TBLPROPERTIES, now complete on every table

Iceberg UniForm, autoOptimize.*, retention durations, enableTypeWidening (Bronze) — all set and verified live via SHOW TBLPROPERTIES. This closed the single biggest mechanical gap — but doing it surfaced a real trade-off, below.

5

Remaining open gaps

Source's created_at column missing, the schema-change runbook untested, Gold's KPI-example columns (data_quality_pct, latest_data_at) not rolled up, external-table recovery practices (`RESTORE TABLE` drills) untested, and no fallback full-scan MERGE / mass-closure monitoring.

The full table-by-table, rule-by-rule breakdown — doc quote, our code, verdict — lives in README.md's "Doc compliance" section. This scorecard is the summary for a live walkthrough; that's the reference to point people at afterward.

Decision needed from stakeholders: Deletion Vectors vs. Iceberg UniForm.

Turning on enableIcebergCompatV2/universalFormat.enabledFormats=iceberg (required to close the TBLPROPERTIES gap above) forced Deletion Vectors off on every table — Databricks blocks the two from coexisting (hit this directly: DELTA_ICEBERG_COMPAT_VIOLATION). This matters far more once real, growing data replaces this 5-row sample:

OptionWhat it costs / buys
Deletion Vectors ON
(Iceberg off)		 Databricks' own recommended default for MERGE-heavy tables — a MERGE/UPDATE/DELETE writes a small marker instead of rewriting whole Parquet files. Bronze runs an SCD2 MERGE on every single incremental load, forever — this is the layer the choice matters most for, and the one growing biggest over time. No external engine (Trino, Snowflake, an Iceberg REST Catalog) can read the table natively as Iceberg.
Iceberg UniForm ON
(current setting, per the doc)		 Matches the doc's TBLPROPERTIES literally. Every MERGE/UPDATE/DELETE must rewrite full Parquet files — negligible on 5 rows, a real and growing cost as Bronze's history accumulates in production. Buys nothing unless something actually reads this table via Iceberg outside Databricks.

The question that actually decides this: does any consumer of this pipeline's tables need to read them as Iceberg from outside Databricks (Trino, Snowflake, an Iceberg REST Catalog, a data-sharing agreement)? Nothing in DAA-856 or this project has named one so far.

Current state: Iceberg UniForm is ON (Deletion Vectors OFF), following the doc literally, per explicit direction to implement it this way and raise the trade-off here rather than decide it unilaterally. This is the one open item worth a direct answer from whoever owns this pattern going into production — reversible either way with an ALTER TABLE SET TBLPROPERTIES + (if re-enabling Iceberg later) a REORG TABLE ... APPLY (PURGE).

The watermark itself — now via job_flags

The doc is explicit: "Don't invent a new _ingestion_control table per pipeline. Reuse job_flags.py." This harness originally did exactly that anti-pattern — fixed now. job_flags is append-only; after an update to ORD-1001 and a second Bronze run, the table holds both the original load's values and the new ones, and get() correctly returns the latest by timestamp:
