Medallion Pipeline Anatomy

A beginner's walkthrough of common/pipeline.py: where tables get created, where they get merged, how a row earns its "fingerprint," and every real conflict this design had to solve to be safe.

00

What is medallion architecture?

Medallion architecture is just a naming convention for a pipeline that gets progressively cleaner and more useful as data moves through it, in three named stops:

Stagingraw source
→
Bronzefull history
→
Silvercurrent & clean
→
Goldbusiness answers
  • STAGING the raw source table. In this harness it's a plain Delta table you (or a real CDC connector) write INSERT/UPDATE/DELETE into directly. Nothing here is cleaned up — it's a mirror of "whatever the source system says right now."
  • BRONZE every version of every row, ever. Bronze never forgets — when a row changes, the old version is marked "closed" and a new version is added. This is what lets you answer "what did order ORD-1001 look like last Tuesday?"
  • SILVER only the current version of each row, cleaned up (trimmed, upper-cased status, data-quality flags added). No history — just "the truth, right now."
  • GOLD business-facing aggregates built from Silver — in this harness, a simple count of orders per status.

The one-line mental model used throughout this document: Bronze remembers everything, Silver knows only "now," Gold answers a business question about "now."

01

The layers & who creates what

Not every layer gets built the same way. This is the single biggest thing to internalize before the MERGE details make sense:

LayerFirst run everEvery run after that
STAGINGNever touched by the pipeline at all — it's CREATE TABLE IF NOT EXISTS once, then only you (or CDC) ever write to it.
BRONZECREATE TABLE IF NOT EXISTS once (empty skeleton). After that, never CREATEd again — every run does a small MERGE (to close old rows) plus a plain APPEND (to add new/changed rows).
SILVERCREATE TABLE ... AS SELECT — a genuine full build, because Silver is empty and there's nothing yet to merge against.Every run after the first is a MERGE — Silver itself is never CREATEd again after that first run.
GOLDCREATE OR REPLACE TABLE — every single run, forever. Gold is small (one row per status), so a full rebuild is cheap and simplest.
Why Silver used to be CREATE OR REPLACE too The very first version of this pipeline rebuilt Silver from scratch on every run, the same way Gold still does. That's fine for a five-row demo but wasteful for real data: if Bronze only had 3 changed rows out of a million, a full rebuild still rewrites every single Parquet file. Switching to MERGE for Silver means Delta only touches the files that actually contain a changed row — this is exactly the split the golden-path doc describes as "initial build" vs. "incremental refresh."
02

How MERGE actually works — two different jobs

This pipeline uses MERGE INTO twice, for two genuinely different purposes. Confusing the two is the most common beginner mistake, so they're laid out side by side.

BRONZE MERGE — "close the old version," nothing else

common/pipeline.py :: run_bronze

MERGE INTO bronze AS t
USING _e2e_close_keys AS s
ON t.order_id <=> s.order_id AND t._bronze_is_current = TRUE
WHEN MATCHED THEN UPDATE SET
    t._bronze_valid_to   = CURRENT_TIMESTAMP(),
    t._bronze_is_current = FALSE

Notice what's missing from the UPDATE SET: customer_name, status, amount — none of the actual business columns. This MERGE only ever touches two bookkeeping columns. It stamps the old row "closed," full stop. It never rewrites what that row used to say, because that would destroy history. The new version of the row is written separately, as a plain append, right after.

SILVER MERGE — a full 3-way sync against "current Bronze"

common/pipeline.py :: run_silver

MERGE INTO silver AS target
USING _e2e_silver_src AS source
ON target.order_id <=> source.order_id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
WHEN NOT MATCHED BY SOURCE THEN DELETE

Here all three clauses matter, because Silver's whole job is to mirror "Bronze's current rows" exactly:

  • MATCHED → UPDATE SET * — the key exists in both: overwrite every column in Silver with the fresh value from Bronze.
  • NOT MATCHED → INSERT * — a brand-new key showed up: add it to Silver.
  • NOT MATCHED BY SOURCE → DELETE — a key used to be in Silver but Bronze no longer marks it current (it was soft-deleted, or its key changed): remove it from Silver. This is safe specifically because _e2e_silver_src is Bronze's full current set, not a partial batch — "missing from source" genuinely means "no longer current," not "just wasn't in today's batch."
The gotcha that drove two real bugs (§6) WHEN MATCHED THEN UPDATE SET * requires the source and target to have the exact same set of columns — not a superset, not a subset. If Silver has one column the source view doesn't (or vice versa), Spark throws DELTA_MERGE_UNRESOLVED_EXPRESSION instead of quietly ignoring it. Section 6 covers exactly how this bit the pipeline.
03

What moves data from one layer to the next

STAGING → BRONZE

  1. A real new commit must exist. run_bronze compares the last processed staging version (the "watermark," stored in job_flags) against staging's latest version. If they're equal, it exits immediately with ran: false — nothing to do.
  2. Only real row-level changes count. Delta's Change Data Feed (CDF) is read for exactly the version range (from_version, to_version], filtered to insert / update_postimage / delete events only.
  3. Multiple changes to the same key collapse to one. If ORD-1001 was updated twice before Bronze got a chance to run, latest_per_key() keeps only the very latest version (see §4).
  4. The hash must actually differ. This is the real gate — see §4: a row whose hash matches the current Bronze row's hash is UNCHANGED and is dropped before either the MERGE or the append runs.

BRONZE → SILVER

  1. Only current rows. df = spark.table(bronze_fqn).filter(F.col("_bronze_is_current")) — history never leaves Bronze.
  2. Every key column must be non-NULL. A row with a NULL key can never be reliably matched again downstream, so it's filtered out defensively before it can cause a bad join later.

SILVER → GOLD

No filtering at all — Gold reads every row currently in Silver and aggregates it (GROUP BY status, COUNT(*)). Whatever data-quality work needed doing already happened in Silver.

04

The hash: how a row gets its fingerprint

This is the part most likely to confuse a beginner, so it's worth being very explicit: order_id and _bronze_hash are two completely different things.

  • order_id is the business key — it identifies which order this is. It comes from the source system.
  • _bronze_hash is a content fingerprint — it summarizes what the row currently says. It's generated by this pipeline, not the source.

common/scd2.py :: row_hash()

def row_hash(business_cols, exclude):
    parts = [
        F.coalesce(F.col(c).cast("string"), F.lit(NULL_SENTINEL))
        for c in sorted(business_cols)
        if c not in exclude
    ]
    return F.md5(F.concat_ws("|", *parts))

Step by step:

  1. Start from every business column — everything in staging except CDF plumbing columns (_change_type, _commit_version, _commit_timestamp, _rescued_data).
  2. Sort the column names alphabetically. This fixes the order once and for all — the hash of a given set of values will always be computed the same way, even if someone reorders columns in the source table later.
  3. Exclude volatile audit columns — here, just updated_at. It's a timestamp the source stamps on every write, real change or not, so including it in the hash would make "I re-saved this row with no actual change" look identical to a genuine business change. That's exactly the kind of noise the hash is designed to ignore.
  4. Cast everything to string, and replace NULL with a private sentinel ("\x1fNULL", a control character that can't appear in normal text). Without this, a NULL customer_name and an empty-string customer_name would produce the same hash input and be treated as identical rows — a real correctness bug the sentinel exists to prevent.
  5. Join every value with "|" and run it through MD5. The result — one fixed-length string — is _bronze_hash.
Why bother hashing at all? The alternative is comparing every business column of the new row against every business column of the current Bronze row, one by one, for every single row in the batch. Comparing one MD5 string instead is dramatically cheaper at scale, and it's exactly what classify() does: _cur_hash != _bronze_hash is the entire "did anything change?" test.
05

Append vs. overwrite, layer by layer

LayerBehaviorWhy
BRONZE Append-only for real data, plus a narrow 2-column in-place update (only _bronze_valid_to / _bronze_is_current). Business columns of an existing row are never rewritten. This is the entire point of Bronze: it's a permanent, growing history. A row can be closed, never edited.
SILVER True upsert + delete via MERGE — rows are updated in place, new ones inserted, stale ones removed. Silver represents "right now," not history — when the truth changes, the old value should genuinely disappear, not stick around.
GOLD Full overwrite (CREATE OR REPLACE TABLE) on every run. Gold here is one tiny aggregate table — cheap to rebuild completely, and simplest to reason about. (The MERGE optimization the doc calls for was scoped to Silver specifically, since that's where the real row-count savings are.)
06

Real-world conflicts & how this pipeline solves them

1. Two updates to the same order, one batch

If ORD-1001 is updated twice before Bronze gets a chance to run, both changes show up in the same CDF read. Without help, this would try to create two new "CHANGED" rows for the same key.

common/scd2.py :: latest_per_key()

w = Window.partitionBy(*keys).orderBy(
    F.col("_commit_version").desc(),
    F.col(sequence_by).desc_nulls_last(),   # e.g. updated_at
    F.col("_commit_timestamp").desc(),
)
df.withColumn("_rn", F.row_number().over(w)).filter(F.col("_rn") == 1)

Fix: a ranking window keeps only the single latest change per key. Result: exactly one new Bronze version, not two.

2. Replaying the same range twice (retry / re-run)

Fix: classify() compares each row's hash against Bronze's current hash for that key. If nothing changed, it's tagged UNCHANGED and dropped before the MERGE or the append ever runs — replaying the exact same range is a safe no-op.

3. A new column appears upstream (ADD)

Bronze handles this for free: its write is a pure append, so .option("mergeSchema", "true") just works, even on serverless compute. Silver can't use the same trick, because spark.conf.set("...autoMerge.enabled", "true") — the config that would let a MERGE auto-widen its target — is explicitly rejected on serverless (CONFIG_NOT_AVAILABLE.SERVERLESS_DELTA_SCHEMA_AUTO_MERGE_ENABLED).

Fix: before the MERGE runs, an explicit loop adds any column present in the source view but missing from Silver:

for f in df.schema.fields:
    if f.name not in target_cols:
        spark.sql(f"ALTER TABLE {silver_fqn} ADD COLUMN `{f.name}` {f.dataType.simpleString()}")

4. A column disappears upstream (DROP)

Confirmed live, not assumed: the moment Silver has a column the source view no longer has, WHEN MATCHED THEN UPDATE SET * throws DELTA_MERGE_UNRESOLVED_EXPRESSION — it does not silently leave the old column stale. Before the fix, any column dropped anywhere upstream would crash every future Silver run, permanently.

Fix: a symmetric loop drops any Silver-only column right before the MERGE:

for col in target_cols - source_cols:
    spark.sql(f"ALTER TABLE {silver_fqn} DROP COLUMN `{col}`")

5. A join's own scratch column leaking into real data

classify() computes _cur_hash purely to compare it against _bronze_hash — it was never meant to leave the function. It was missing from the final .drop(...) call, so it silently rode along through Bronze's mergeSchema append, and from there into Silver via the new ADD-missing-columns loop. Found via DESCRIBE TABLE on the live tables, showing a column that shouldn't have existed.

Fix: added to the drop list — .drop(*[f"_cur_{k}" for k in keys], "_cur_hash").

6. A client changes the primary key

The real danger lives in the MERGE's ON clause, which uses null-safe equality (<=>) so that keys are compared correctly even when one side has legacy NULLs. But that safety only helps when both sides are NULL — the instant a new key column is added and every pre-existing "current" row has NULL there while new incoming rows have a real value, NULL <=> 'EU' evaluates to FALSE. Old and new rows silently stop matching: instead of one CHANGED row, you'd quietly get a duplicate "NEW" row and an orphaned, permanently-open old one.

Fix: common/pk_migration.py::check_key_change_readiness() is a read-only pre-flight check — is the candidate key present everywhere, and does it have zero NULLs among current rows? Only flip ENTITY_CONFIG["keys"] once it reports safe: true, after backfilling the new key column through staging as an ordinary UPDATE (never edited directly in Bronze).

7. Silver silently drifting out of sync with Bronze

Fix: the last thing run_silver does is compare row counts and raise immediately if they don't match — a hard stop rather than a silent drift:

if n_silver != n_bronze_current:
    raise AssertionError(f"Silver/Bronze reconciliation failed: ...")
07

Schema evolution & the audit log

Two separate mechanisms cooperate here — one that lets the schema actually change, and one that writes down that it did.

Letting the schema change

LayerMechanismWhy this one
BRONZE.option("mergeSchema", "true") on the append writerPure appends can auto-widen safely, and this option works even on serverless compute.
SILVERExplicit ALTER TABLE ADD/DROP COLUMN loops, run before the MERGEA MERGE can't rely on the session-level auto-merge config on serverless, so the target schema has to be made to match the source before the MERGE ever runs.

Writing it down: common/schema_audit.py

Every layer's schema gets snapshotted as a simple dictionary — {column_name: type} — and that snapshot is stashed as a JSON string inside the generic job_flags key-value table (reusing the same mechanism the watermark uses, rather than inventing a new control table).

common/schema_audit.py :: detect_and_log()

current = _current_schema(spark, table_fqn)              # {col: type} right now
previous = json.loads(job_flags.get(..., key, None))       # {col: type} last time we looked

# diff: anything new → COLUMN_ADDED, anything missing → COLUMN_DROPPED,
# same name different type → TYPE_CHANGED

Every detected change is appended to a real table, schema_audit_log, and the stored snapshot is updated so the next run diffs against today's shape, not the original one. This is called at four points:

  • STAGING — checked at the very start of run_bronze, since the pipeline never writes to staging itself; this is the only place drift there would ever be noticed.
  • BRONZE — checked right after its write, so a mergeSchema-driven widening from that very run is caught immediately, not one run late.
  • SILVER — checked right after its MERGE (or CREATE), covering both ADDs and DROPs.
  • GOLD — checked right after its rebuild.
08

Function-by-function walkthrough

ensure_environment(...)

Idempotent setup, called at the top of every run_* function. It never seeds data — that's a separate concern deliberately kept out of this function, so a test can wipe data without re-creating schemas every time.

  • CREATE SCHEMA IF NOT EXISTS for all 5 schemas (stg/bronze/silver/gold/audit).
  • CREATE TABLE IF NOT EXISTS for staging and Bronze only — Silver and Gold are deliberately not created here, because their very first build needs real data to select from.
  • Ensures the control table (watermarks) and the audit-log table both exist.

reset_environment(...)

Empties every table this harness owns — for a genuine clean slate between test runs.

Why TRUNCATE, not DROP For an external table, DROP TABLE only removes Unity Catalog's metadata entry — the physical Delta files at the fixed S3 location survive untouched. A later CREATE TABLE IF NOT EXISTS at that same path would silently resurrect the old data instead of starting fresh. TRUNCATE empties a table's current data regardless of managed vs. external, so it's the only reset that's actually reliable here. The tradeoff: TRUNCATE clears data, never schema — a column added by ALTER TABLE during a test survives every reset forever, which is why the newer test files clean up their own added columns in a finally block.

run_bronze(...)

  1. ensure_environment(...) — guarantee the skeleton exists.
  2. schema_audit.detect_and_log(..., "staging_orders", ...) — check staging for drift before anything else happens this run.
  3. Compare staging's latest Delta version to the stored watermark. Equal → return immediately, ran: false. This is the idempotency/no-op guarantee.
  4. scd2.read_changes(...) — pull the CDF slice (from_version, to_version].
  5. scd2.latest_per_key(...) — collapse multiple changes to the same key within this batch to just the latest.
  6. scd2.row_hash(...) — compute _bronze_hash for every incoming row.
  7. scd2.classify(...) — tag each row NEW / CHANGED / DELETED / UNCHANGED against current Bronze.
  8. Split into to_close (CHANGED + DELETED — the old version needs closing) and to_insert (CHANGED + NEW — a fresh current row is needed). Deleted rows are closed but never re-inserted — a soft delete, not a hard delete out of history.
  9. If anything needs closing: the "close" MERGE from §2 runs, then logger.log_merge(...) records the operation metrics to audit_log.
  10. If anything needs inserting: drop only the known-never-belongs-in-Bronze columns (CDF plumbing + classify()'s temporary _action tag) — not a fixed target-column list, so any genuinely new business column survives and rides through on mergeSchema instead of being silently discarded. Then append with mergeSchema=true.
  11. control.set_watermark(...) — advance the watermark only after both writes above succeed, so a crash mid-run doesn't lose or double-process a range.
  12. schema_audit.detect_and_log(..., "bronze_orders", ...) — checked after the write, so a mergeSchema widening from this very run is caught immediately.

run_silver(...)

  1. Read Bronze, filtered to _bronze_is_current, and to non-NULL keys.
  2. Cleansing: status trimmed and upper-cased; _is_missing_customer_name / _is_incomplete data-quality flags computed.
  3. Rename Bronze's audit columns into Silver's own naming (_bronze_valid_from → _record_effective_date, etc.) and drop the raw Bronze metadata columns — Silver shouldn't expose Bronze's internal bookkeeping column names directly.
  4. createOrReplaceTempView("_e2e_silver_src") — this view is "Bronze's current state," the thing both the CREATE and the MERGE below read from.
  5. If Silver doesn't exist yet: CREATE TABLE ... AS SELECT * FROM _e2e_silver_src — the one and only full build.
  6. Otherwise: the ADD-missing-columns loop, then the DROP-stale-columns loop (§6, conflicts 3 & 4), then the 3-way MERGE from §2, then logger.log_merge(...).
  7. schema_audit.detect_and_log(..., "silver_orders", ...).
  8. The reconciliation check: silver_rows must equal bronze_current, or raise immediately (§6, conflict 7).

run_gold(...)

  1. CREATE OR REPLACE TABLE ... AS SELECT status, COUNT(*) AS order_count ... GROUP BY status — the entire aggregation, rebuilt fresh every run.
  2. logger.audit(...) wraps the write as a FULL_REFRESH action in the audit log.
  3. schema_audit.detect_and_log(..., "gold_orders_status_summary", ...).
  4. Returns row counts for both Gold and Silver, plus the summed total, so a caller (or a test) can sanity-check the aggregate against the row it was built from.

There is deliberately no separate Gold history table in this harness — the golden-path doc marks that as optional ("build it only if you have a consumer for point-in-time queries"), and Bronze already holds the full history regardless, so one could be added later with zero backfill.

Cheat sheet

QuestionAnswer
Which layers get CREATEd more than once?Only Gold — every single run.
Which layer is append-only?Bronze (business columns never rewritten; only 2 bookkeeping columns get updated in place).
Which layer uses MERGE for a full upsert+delete sync?Silver only.
What decides if a row is "new data" vs. "nothing changed"?_bronze_hash compared against the current row's stored hash.
What's excluded from the hash, and why?updated_at — a re-stamped timestamp with no real change shouldn't count as a change.
How does a new column survive into Bronze?mergeSchema=true on the append write.
How does a new column survive into Silver?An explicit ALTER TABLE ADD COLUMN loop before the MERGE (serverless can't auto-merge a MERGE's schema).
What happens if a column disappears upstream?Silver drops it too, via a symmetric ALTER TABLE DROP COLUMN loop — otherwise the MERGE crashes forever.
Where is every schema change written down?schema_audit_log, via common/schema_audit.py, checked on staging/bronze/silver/gold every run.
What's the actual danger in a primary-key change?Null-safe equality (<=>) doesn't help when the old rows have NULL and the new rows have a real value — they silently stop matching. Check readiness first with pk_migration.py.
